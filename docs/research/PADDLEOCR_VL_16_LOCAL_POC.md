# PaddleOCR-VL 1.6 本地票据 PoC

日期：2026-09-01  
状态：完整官方管线与混合分类均已离线测试，未接入报销主流程

## 结论

PaddleOCR-VL 1.6 在这组复杂普通发票上，版面理解和总金额识别明显优于通用 2B 视觉模型：9 张非空票据的价税合计全部提取正确。但当前 Apple M5 Pro CPU 路径平均需要 45.14 秒/张，模型初始化后 RSS 约 9.5 GiB，测试峰值约 11.4 GiB，因此不适合直接替换当前默认 OCR；即使当前 OCR worker 允许 5 GiB 虚拟地址空间，其常驻内存仍受 3 GiB 容器上限约束。

“PaddleOCR-VL 1.6 提取全文 + Qwen3-VL 2B 文本分类”可以工作：9 张分对 8 张，分类仅增加约 0.22 秒/张。唯一失败样本的票面项目名没有被 1.6 读出，文本中只剩“代开”等弱信息，后置分类模型无法补回上游丢失的关键字。

当前建议：继续以现有 PP-OCRv6 + 确定性 Parser 为默认路径；若后续真实失败样本证明值得，再把 1.6 作为独立、单并发的低置信度兜底，而不是每张票据都调用。

## 测试范围

- 设备：Apple M5 Pro，48 GB 统一内存。
- 推理：官方完整 `PaddleOCRVL(pipeline_version="v1.6")`，PaddlePaddle CPU；启用布局检测，关闭方向、去畸变、图表和印章等本轮不需要的模块。
- 版本：Python 3.11、`paddlepaddle==3.3.1`、`paddleocr==3.7.0`。
- 样本：10 张独立图片；1 张为空白航空票样，不参与字段准确率；9 张有效票据覆盖广告、通讯、劳务、餐饮、租赁、住宿、办公和水费。
- 金标准：人工确认的费用类别与价税合计。
- 金额计算：模型输出结构化表格后，按“价税合计（小写）/ 价税合计 / 合计”优先级做确定性提取，不采用模型自由生成的最终 JSON。
- 分类对照：把 1.6 输出的文字交给本机 `qwen3-vl:2b-instruct-q4_K_M`，只允许返回一个公司费用类别 ID。

以上为 2026-09-01 的历史结果。当时有一张文件目录误标为“咨询”、票面实际为“劳务费”的样本；该重复劳务样本已于 2026-09-02 从本地测试集和复现实验脚本移除，历史统计不追溯改写。

本轮没有足够的“开票日期与实际发生日期同时出现”的新样本，因此没有统计发生日期准确率。它不能由金额结果推导，仍应使用现有火车票、打车票据和今后新增的多日期样本单独回归。

## 结果

| 方案 | 类别精确匹配 | 总金额精确匹配 | 平均耗时 | 资源与观察 |
|---|---:|---:|---:|---|
| 当前 PP-OCRv6 + 金额规则 | 未扩展新类别 Parser | 8/9 | 本轮未重测 | 唯一金额错误为把 14.56 税额当成 500.00 总额 |
| MiniCPM-V 4.6 Q4 图片直出 | 1/9 | 4/9 | 1.34 秒/张 | 快，但不稳定 |
| Qwen3-VL 2B Q4 图片直出 | 7/9 | 7/9 | 0.99–2.28 秒/张 | 两次热态运行有波动；会选中未税金额或税额 |
| **PaddleOCR-VL 1.6 + 确定性金额提取** | 不直接输出公司类别 | **9/9** | **45.14 秒/张** | 初始化 RSS 9.5 GiB；峰值 11.4 GiB |
| **PaddleOCR-VL 1.6 + Qwen3-VL 2B 文本分类** | **8/9** | 沿用上行 9/9 | 额外 0.22 秒/张 | 分类输出 10/10 均符合 Schema |

PaddleOCR-VL 1.6 的单张中位耗时为 47.05 秒，管线初始化约 5.23 秒。其官方模型缓存约 1.9 GiB；本轮隔离 Python 环境约 1.0 GiB。`uv` 下载缓存另占约 1.0 GiB，可以在不影响运行的情况下另行清理。

## 关键观察

1. **1.6 的优势是结构化读文档。** 它保留了表格行、字段标签、块坐标和布局类别，使确定性规则能定位“价税合计”，避免把税额、未税金额、单价或发票号码当成报销金额。
2. **速度和内存是当前硬限制。** 45 秒/张意味着一次上传 10 张票据约需数分钟；11.4 GiB 峰值也远超当前容器预算。开发机能跑不代表目标 Linux CPU 服务器适合在线运行。
3. **后置小模型适合模糊语义，不适合补 OCR 漏字。** 当原文包含“市场推广费”“通信服务费”“房租”“住宿服务”“文具”“居民用水”等证据时，2B 模型能正确分类；项目名缺失时应返回“其他”让用户修改。
4. **已知类别优先写 Parser 更划算。** 本轮分类 Prompt 中必须明确“房租=租赁费、文具=办公费”等类别定义，这些稳定映射本身就可以写成更快、可测试、可解释的规则。小模型只在规则命中冲突或返回 `other` 时才可能有额外价值。
5. **不能让 1.6 或分类模型直接写 Excel。** 金额、发生日期、类别都仍需 Schema、`Decimal`、证据和业务规则校验，用户保留编辑能力。

## 工程决策

现在不修改默认 OCR 流程，也不把 1.6 加入 Docker 镜像。若扩大样本后确认它能显著减少人工修改，建议只增加一个窄接口：

```text
现有 PP-OCRv6 + Parser
  -> 字段完整且规则明确：直接返回
  -> 缺金额 / 缺发生日期 / 类别为 other：调用独立 PaddleOCR-VL 1.6 worker
  -> 确定性字段校验
  -> 用户编辑
```

1.6 worker 应独立于 FastAPI 和现有 OCR worker，单并发、设置超时并允许安全回退。是否需要 Qwen 2B 分类器，应等 Parser 补齐稳定类别后再比较；不能只因为本轮达到 8/9 就增加第二个常驻模型。
